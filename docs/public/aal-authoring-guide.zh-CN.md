# AAL 编写指南

> 默认英文版本：[AAL Authoring Guide](./aal-authoring-guide.md)

## 语言定位

AAL（Auditable Application Language，可审计应用语言）是一种面向应用行为、给人审计的正式语言。

它描述：

- 世界中有哪些数据和状态；
- 流程会进行哪些计算和判断；
- 哪些状态会被明确改变；
- 多个业务流程如何组合；
- 成功输出和失败条件是什么。

用户确认 AAL 后，确定性解析器、语义检查器和 TypeScript 生成器负责后续处理，不再让 LLM 推断缺失的业务决定。

## 方言

英文是默认方言，无语言后缀的文件使用英文。

中文文件使用 `.zh-CN.aal` 后缀，并通过 `--language zh-CN` 编译。

两种方言进入同一套 AST、检查器、Binding 解析和代码生成流程；它们只是同一核心语义的两种人类表层。

## 给生成 AAL 的 AI 的规则

1. 只输出 AAL，不要把 TypeScript、JavaScript 或伪代码当成 AAL。
2. 应用标题后，用户表层只使用 `取值`、`对象`、`流程` 和 `HTTP 入口` 四种顶层声明。
3. 字段关系统一写成 `库存 的 数量`，不要使用点号、方括号、`this`、方法或调用等实现语法。
4. 不要自行补全字段、类型、币种、单位、精度、权限、重试、并发、回滚、舍入或失败行为。
5. 每个对象字段和流程输入都必须有明确类型。
6. 真实状态变化必须写在 `改变` 下；计算本身不会改变对象。
7. 优先生成小型、单一职责、可组合的流程；一个流程尽量只表达一个可以用自然语言命名的业务动作或判断。
8. 流程组合必须显式写出 `执行`、`使用` 和 `得到`。
9. 业务需求存在歧义时先询问用户。
10. 用户确认 AAL 后，停止继续改变业务含义。

## 文件结构

每个文件必须从一个应用标题开始。P0 至少需要一个对象和一个流程：

```aal
应用：库存应用

对象：库存

    数量：整数

流程：读取库存

    输入：
        库存：库存

    输出：
        数量 = 库存 的 数量
```

每层缩进使用 4 个空格。空行和以 `#` 开头的行会被忽略。

应用、对象、流程、字段和输入名称必须以字母或下划线开始，后面只能包含字母、数字或下划线；Unicode 汉字属于字母。HTTP 入口的审计标题可以包含空格。

## 对象与字段

对象只描述数据和状态，不包含流程：

```aal
对象：订单

    编号：整数

对象：库存

    数量：整数
```

读取多层字段时使用 `的`：

```text
订单 的 编号
订单 的 用户 的 姓名
```

`订单.编号` 这样的点号访问会被拒绝。

用于 CRUD 的对象必须明确声明身份：

```aal
对象：项目

    编号：整数
    名称：文本

    身份：
        编号
```

当前 MVP 不会自动生成 ID。创建相同身份的对象会失败，创建后也不能改变身份字段。

## 类型

当前语言支持以下声明：

```text
整数
文本
布尔
时间
人民币金额
美元金额
已声明取值的名称
已声明对象的名称
```

例如，声明 `对象：库存` 后，`库存` 就可以作为类型使用。“对象名称”四个字本身不是类型关键字。

内置金额类型当前使用固定标准表示：

```text
人民币金额 = 币种 CNY，单位 yuan，2 位小数
美元金额 = 币种 USD，单位 dollar，2 位小数
```

也可以明确写出单位标签：

```aal
单价：人民币金额，单位为元
```

编译器会把内置的 `元` 和 `美元` 归一化为运行时使用的 `yuan` 和 `dollar`。P0 的金额精度仍固定为两位小数，暂不支持自定义精度。非标准单位必须来自用户确认的业务需求，不能由 AI 或编译器猜测。

表达式支持整数常量和精确到两位小数的金额常量：

```aal
如果 金额 <= 0.00 元：
    失败：金额必须大于零
```

文本和布尔常量语法尚未实现。有限业务取值应通过 `取值` 声明，而不是使用任意文本。

## 流程

流程描述应用中会发生什么：

```aal
流程：扣减库存

    输入：
        库存：库存
        数量：整数

    如果 数量 <= 0：
        失败：数量必须大于零

    如果 库存 的 数量 < 数量：
        失败：库存不足

    改变：
        库存 的 数量 = 库存 的 数量 - 数量

    输出：
        剩余库存 = 库存 的 数量
```

每个流程都必须有 `输出`。`如果` 的条件必须是布尔条件，其内容可以是一条明确的 `失败`，也可以是继续缩进的业务步骤。被执行流程失败时，同一个失败结果会传递给当前流程。

### 可组合审计流程

在语义密集的业务中，单个长流程仍然可能变得难以阅读。当前推荐的组织方式是把它拆成小型、单一职责、可组合的流程，再由主流程按业务顺序组合。这样主要改善局部审计和后续增量审计的难度，不一定减少总行数，也不代表语义密集流程的可读性问题已经解决。

当一个流程同时承担查询、资格判断、金额检查、计算和状态修改等多个可以独立命名的职责时，AI 应优先拆成小流程，再由一个主流程按业务顺序组合。例如：

```text
退款订单
├── 获取退款上下文
├── 检查退款资格
├── 检查退款金额
└── 执行退款
```

拆分后的每个流程应满足：

1. 名称能直接说明一个业务动作或判断；
2. 输入和输出是业务数据，不暴露数据库连接、框架对象或异常结构；
3. 失败条件集中在负责该判断的流程中；
4. 主流程主要用于展示执行顺序和组合关系；
5. 不把一个简单表达式机械拆成流程，也不创建没有独立审计价值的包装流程。

第一次审计需要展开所有相关小流程。以后规则变化时，可以主要复审发生变化的小流程及其调用关系。HTTP 入口通常只连接主流程，内部小流程不需要对外暴露。

显式的 `执行 / 使用 / 得到` 连接可以让组合关系更清楚，但也会增加主流程中的连接文本。这是当前语言设计的待优化限制，不应被包装成已经解决的问题。

流程拆分与状态提交原子性是两件事。多个状态必须一起改变时，仍使用 `同时生效`；不要因为流程被拆小就省略失败原子性。

## 计算与状态改变

计算会命名一个派生值，但不会修改状态：

```aal
计算：
    总价 = 单价 * 数量
```

只有 `改变` 表示真实对象状态发生变化：

```aal
改变：
    库存 的 数量 = 库存 的 数量 - 数量
```

`改变` 的目标必须是对象字段。输入、计算结果和流程输出不能被直接修改。

## 有限取值、时间与同时生效

有限业务取值必须明确声明：

```aal
取值：订单状态
    未支付
    已支付
    已全部退款
```

取值成员不是任意文本。不同取值类型的成员不能相互比较或赋值。

`时间` 表示 UTC 时间点；`7 天` 这样的持续时间固定为 7 × 24 小时。HTTP 入口可以提供客户端不能伪造的当前时间：

```aal
系统提供：
    当前时间 作为 操作时间
```

多个创建和改变必须一起提交时使用 `同时生效`：

```aal
同时生效：
    改变：
        订单 的 状态 = 已支付
        库存 的 数量 = 库存 的 数量 + 数量
```

内存 Runtime 会先暂存整个区块、验证所有创建，再统一提交。这不等价于数据库隔离级别或分布式事务保证。

## 流程组合

执行另一个业务流程时必须显式写出：

```aal
执行：
    计算订单总价

    使用：
        单价
        数量

    得到：
        总价
```

`使用` 按被执行流程声明的输入顺序对应参数；`得到` 按输出顺序接收结果。编译前会检查输入数量、输出数量和类型。

## 创建、查询、改变与删除

CRUD 行为仍然写在流程中：

```aal
流程：修改项目

    输入：
        编号：整数
        名称：文本

    查询：
        项目：项目

        条件：
            项目 的 编号 == 编号

        否则：
            失败：项目不存在

    改变：
        项目 的 名称 = 名称

    输出：
        项目
```

`创建` 必须给全部字段赋值，并声明身份重复时的失败；`查询` 只返回一个对象，并声明未找到时的失败；`删除` 移除先前创建或查询到的对象。当前运行时只把对象保存在内存中。

完整的中文创建、读取、修改和删除流程见 [examples/items/app.zh-CN.aal](../../examples/items/app.zh-CN.aal)。

## HTTP 入口

HTTP 入口把请求数据映射到一个流程：

```aal
HTTP 入口：修改项目

    接收：
        PUT /items/{id}

    使用流程：
        修改项目

    请求路径：
        id 作为 编号

    请求体：
        name 作为 名称

    成功：
        返回 200

    如果 项目不存在：
        返回 404
```

流程的每个输入必须恰好映射一次。HTTP 字段名称默认与 AAL 输入名称相同；不同时通过局部 `作为` 映射明确写出。

可信时间输入单独写在 `系统提供` 下，不能同时来自路径或请求体。HTTP 金额输入使用 `"100.00"` 这样的固定两位字符串，金额输出使用相同表示。

当前 MVP 固定以下传输语义：非法 JSON、输入缺失或类型错误返回 `400`；路由未匹配返回 `404`；流程声明的失败使用 AAL 映射的状态码；未处理运行时错误返回 `500`；成功的 `204` 响应没有响应体。Host 和 Port 只在启动时指定，不写入 AAL。

## 表达式与运算符

解析器识别：

```text
+  -  *  /  %  >  >=  <  <=  ==  !=  并且  或者  非  (  )
```

`=` 用于计算、改变和命名输出；相等比较使用 `==`。

P0 类型检查允许：

- 整数算术；
- 币种、单位和精度完全一致的金额相加或相减；
- 金额与整数按任意顺序相乘；
- 兼容类型之间的比较；
- 时间加上 `7 天` 这样的持续时间；
- UTC 时间比较；
- 布尔 `并且`、`或者` 和 `非`。

整数 `/` 当前沿用生成 TypeScript 的数值除法语义。长期的整数舍入规则尚未正式定义；如果结果可能出现小数，在业务规则单独确认前不要使用它。

## Binding

AAL 默认直接使用审计名称。可选的 [Binding 文件](./binding-guide.zh-CN.md)可以把 `订单` 下的审计字段 `编号` 保持为稳定 ID，同时生成程序字段 `id`。

不提供 Binding 时，审计名称同时也是程序名称，编译器为本次构建生成确定性的临时 ID。只有名称需要不同，或身份需要跨源文件重命名、声明顺序变化保持稳定时，才使用显式 Binding。

Binding 是独立构建输入，不能增加隐藏业务规则。

## 完整示例与编译

基础中文示例位于 [examples/order/app.zh-CN.aal](../../examples/order/app.zh-CN.aal)。语义密集型示例位于 [examples/order-refund/app.zh-CN.aal](../../examples/order-refund/app.zh-CN.aal)。

```bash
npm run compile:example:zh
```

当前 P0 将最后声明的流程作为生成程序的 `run` 入口。未来的多入口协议必须显式声明，不能依靠名称猜测。

运行 HTTP CRUD 示例：

```bash
npm run demo:http
```

运行订单退款冻结 Oracle：

```bash
npm run test:order-refund
```

## 当前 P0 限制

P0 尚未提供：

- 文本或布尔常量；
- 自定义金额精度；
- 持久化、数据库事务、自动 ID、列表查询或筛选；
- 第三方 API、SDK 或数据库适配；
- PATCH、CORS、鉴权、重试、并发或权限。

不要使用隐藏约定模拟这些能力。

## 审计清单

- [ ] 文件是否从唯一的应用标题开始？
- [ ] 其余顶层声明是否只有取值、对象、流程和 HTTP 入口？
- [ ] 每个对象字段和流程输入是否都有类型？
- [ ] 每个金额是否明确人民币或美元，非标准单位是否经过确认？
- [ ] 每个字段关系是否使用“的”，而不是点号？
- [ ] 所有状态变化是否显式写在“改变”中？
- [ ] 多对象必须一起成功的改变是否显式写在“同时生效”中？
- [ ] 所有流程组合是否写明“执行 / 使用 / 得到”？
- [ ] 所有失败条件和消息是否明确？
- [ ] 每个 CRUD 对象是否声明了身份？
- [ ] 每个 HTTP 入口是否明确映射了全部流程输入和失败？
- [ ] AI 是否避免自行补全业务决定？
