# 订单退款示例所需的 AAL 语言能力增量 v1

状态：**设计候选，尚未实现**

本文件只定义第一里程碑所需的最小语义增量。所有语义必须进入中英文共用 AST、语义检查器和 Runtime；中文只是一种表层方言。

## 1. 设计原则

1. 业务规则必须在 AAL 中可见。
2. 精确金额、时间比较和原子提交可以由语言标准统一保证，但保证必须有文档和确定性测试。
3. Runtime 不得根据流程名称、字段名称或 HTTP 路径推断退款行为。
4. 不为第二里程碑提前加入可选查询、结果重放或通用事务框架。
5. 每个新增构造只服务于已冻结需求。

## 2. 领域取值

新增顶层业务声明候选：

```aal
取值：订单状态
    未支付
    已支付
    已取消
    已全部退款

取值：用户角色
    普通用户
    管理员
```

使用：

```aal
对象：订单
    状态：订单状态
```

语义：

- 取值不是任意文本，也不等价于整数代码；
- 只能赋值或比较声明过的取值；
- 不同取值类型之间不能比较；
- 编译器不得为取值增加未声明成员；
- Binding 未来可以改变程序名称，但不能改变审计取值的身份和含义。

对应 AST 需要一等的 `ValueSetDeclaration`、`ValueType` 和 `ValueLiteral`，不能降级为普通文本。

## 3. 精确金额表达式与 HTTP 编码

现有 `人民币金额` 继续固定为 CNY、yuan、两位小数、最小单位精确存储。

新增金额常量：

```aal
0.00 元
100.00 元
```

第一里程碑需要支持：

```text
人民币金额 + 人民币金额
人民币金额 - 人民币金额
人民币金额 × 整数
人民币金额之间的 ==、!=、<、<=、>、>=
```

不同币种、单位或精度之间的运算必须在编译前失败。

HTTP 输入和输出使用固定两位小数的十进制字符串：

```json
"100.00"
```

拒绝：

```text
100
100.0
100.000
1e2
"100"
"1e2"
"￥100.00"
```

生成的 JSON 不能暴露内部 bigint、币种对象或实现结构。

## 4. 时间、持续时间与可信时钟

新增：

```text
时间
持续时间
7 天
```

第一里程碑只支持：

```text
时间 + 持续时间 → 时间
时间之间的 ==、!=、<、<=、>、>=
```

`天` 固定为 24 小时，不引入日历、时区、夏令时或自然月语义。

HTTP 入口需要显式声明可信 Runtime 上下文映射，候选表层为：

```aal
系统提供：
    当前时间 作为 操作时间
```

对应流程仍然显式声明：

```aal
输入：
    操作时间：时间
```

因此审核者可以看到流程依赖时间，同时 HTTP 客户端不能伪造该输入。

生产运行时从系统 UTC 时钟提供当前时间；测试运行时必须注入冻结时钟。时钟来源和摘要写入测试结果。

## 5. 逻辑运算

新增中文运算符：

```text
并且
或者
非
```

优先级固定为：

```text
括号
非
比较
并且
或者
```

例如：

```aal
如果 用户 的 角色 != 管理员 并且 操作时间 > 支付记录 的 支付时间 + 7 天：
    失败：已超过普通用户退款期限
```

英文方言必须映射到同一 AST 运算符，不能有不同求值顺序。

## 6. 条件业务步骤

现有 `如果` 只能紧跟失败。第一里程碑需要让条件内部包含普通业务步骤：

```aal
如果 订单 的 状态 == 未支付：
    同时生效：
        改变：
            订单 的 状态 = 已取消
            库存 的 库存数量 = 库存 的 库存数量 + 订单 的 购买数量
```

语义：

- 条件为真时按声明顺序执行内部步骤；
- 条件为假时跳过整个区块；
- 条件区块可以包含计算、创建、改变和同时生效；
- 第一里程碑不加入循环、模式匹配或提前成功返回；
- `如果 ... 失败` 仍保持现有守卫语义和声明顺序。

这允许重复取消在状态已取消时自然跳过改变，并在流程末尾返回当前结果。

## 7. 同时生效

新增显式原子区块候选：

```aal
同时生效：
    创建：
        支付记录：支付记录
        ...

    改变：
        订单 的 状态 = 已支付
```

语言标准保证：

1. 区块内创建和改变全部通过后一次性提交；
2. 任一步骤失败或抛出运行时错误时全部放弃；
3. 区块不能观察到自身的部分提交状态；
4. 同一流程在提交前的查询和计算不会修改存储；
5. 生成后端必须通过暂存变更实现，不能依赖语句碰巧不失败。

第一里程碑只要求单进程内存 Runtime 的原子提交，不承诺数据库隔离级别、并发冲突处理或分布式事务。

对应 AST 应使用显式 `AtomicStatement`，不能仅在代码生成阶段根据相邻 `change` 猜测。

## 8. 流程顺序与错误优先级

流程守卫按 AAL 从上到下求值。第一个失败立即终止流程，后续守卫、计算和改变都不执行。

这条规则使错误优先级直接由 AAL 顺序可审计。编译器不得重排可能失败的查询或守卫。

语义检查器需要拒绝：

- 在要求优先的守卫之前产生状态变化；
- 在原子区块外混入属于同一原子业务操作的改变；
- 把可能失败的创建放在非原子改变之后。

## 9. Fixture 注入边界

Fixture 是运行输入，不是 AAL 行为。

CLI 后续需要提供类似：

```text
--fixture <path>
--clock <frozen UTC instant>
```

Fixture 加载必须：

- 在服务接收请求前完成；
- 使用 AAL 对象、字段和类型进行验证；
- 拒绝重复身份、未知字段和不合法取值；
- 不触发业务流程或状态变化；
- 把 fixture 摘要写入测试结果。

Fixture 内容不计入应用行为审计面积，但必须作为测试输入单独可见、可复现。

## 10. HTTP 输出编码

新增类型必须拥有确定性外部编码：

```text
领域取值 → 审计取值文本
人民币金额 → 固定两位十进制字符串
时间 → ISO 8601 UTC 字符串
```

对象和流程输出继续使用 Binding 或确定性默认名称。输出字段顺序不能影响行为指纹。

## 11. 明确不进入第一里程碑

```text
requestId 幂等
可选查询
提前成功返回
退款结果重放
数据库持久化
并发事务
认证与授权上下文
多币种兑换
日历时间
列表查询
通用异常捕获
```

这些能力只有在对应业务规格冻结后才能增加。

## 12. 实现顺序

建议垂直实现：

1. 领域取值和常量；
2. 金额常量、运算及 HTTP 编码；
3. 时间、持续时间和冻结时钟；
4. 逻辑运算；
5. 条件业务步骤；
6. 同时生效；
7. Fixture 注入；
8. 中文订单退款 AAL；
9. 冻结 Oracle；
10. 真人审计测试。

每一步都必须同时具备 AST、Parser、Checker、Codegen/Runtime、中英文方言映射和确定性测试。
