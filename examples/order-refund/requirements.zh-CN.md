# 订单退款与库存回补：冻结业务规格 v1

状态：**已人工确认并由冻结 Oracle 实现**

本规格是第一里程碑的业务权威来源。冻结 HTTP Oracle 从这里派生；编译器、Runtime 和生成代码不得补充这里没有声明的业务决定。

## 1. 目标

用四个 HTTP 入口承载以下业务语义：

- 订单状态机；
- 精确人民币金额；
- 普通用户与管理员的退款规则；
- 支付后 7 天边界；
- 支付、取消和退款造成的多对象状态变化；
- 明确错误优先级；
- 失败时不发生部分修改；
- 重复取消不重复回补库存。

第一里程碑不包含 requestId 幂等、持久化、并发、鉴权、订单创建、自动 ID、列表查询或数据库事务。

## 2. 业务取值

订单状态只能是：

```text
未支付
已支付
已取消
已全部退款
```

用户角色只能是：

```text
普通用户
管理员
```

不允许使用任意文本或整数代码代替这些业务取值。

## 3. 数据

### 订单

```text
编号：整数，身份
状态：订单状态
商品编号：整数
商品单价：人民币金额
购买数量：整数
已退款数量：整数
已退款金额：人民币金额
```

### 支付记录

```text
订单编号：整数，身份
支付金额：人民币金额
支付时间：时间
```

未支付订单没有支付记录。支付成功时创建支付记录，因此不使用 `0` 或空文本伪造“尚未支付”的时间。

### 商品库存

```text
商品编号：整数，身份
库存数量：整数
```

### 用户

```text
编号：整数，身份
角色：用户角色
```

## 4. 数据不变量

任何成功状态下都必须满足：

```text
商品单价 > 0
购买数量 > 0
已退款数量 >= 0
已退款数量 <= 购买数量
已退款金额 >= 0 元
已退款金额 <= 支付金额（存在支付记录时）
```

订单 fixture 表示订单创建已经发生，购买数量已经从库存扣除或占用。因此：

- 取消未支付订单会回补全部购买数量；
- 退款会回补本次退款数量；
- 重复取消不能再次回补；
- 支付本身不再次扣减库存。

处于 `已支付` 或 `已全部退款` 的订单必须存在支付记录。缺失支付记录属于内部数据不一致，不是普通业务失败。

## 5. 金额与时间

所有金额都是 `人民币金额`，固定两位小数，内部按最小货币单位精确计算，不使用二进制浮点近似。

HTTP 中人民币金额使用十进制字符串：

```json
"100.00"
```

不接受 JSON number、科学计数法、多于或少于两位小数、币种后缀或千位分隔符。

时间表示 UTC 时间点。HTTP 输出使用 ISO 8601 UTC 字符串，例如：

```text
2026-01-08T00:00:00.000Z
```

操作时间由可信 Runtime 时钟提供，不由 HTTP 请求体提供。Oracle 必须注入固定时钟。

普通用户退款窗口定义为：

```text
操作时间 <= 支付时间 + 7 天
```

支付后第 7 天整仍允许退款；超过该时间才失败。`7 天` 固定为 7 × 24 小时，不使用本地日历日。

## 6. HTTP 入口

```text
POST /orders/{id}/pay
POST /orders/{id}/cancel
POST /orders/{id}/refund
GET  /orders/{id}/refundable
```

业务对象、字段、流程和错误使用中文审计名称。路径和请求字段使用稳定的外部英文名称，通过 HTTP 局部映射连接，不要求业务 AAL 使用英文名称。

### 6.1 支付订单

请求：

```http
POST /orders/{id}/pay
Content-Type: application/json
```

```json
{
  "amount": "200.00"
}
```

错误检查顺序：

1. 订单不存在 → `404`，`订单不存在`；
2. 订单状态不是 `未支付` → `409`，`订单状态不允许支付`；
3. 支付金额小于或等于 0 → `400`，`支付金额必须大于零`；
4. 支付金额不等于 `商品单价 × 购买数量` → `409`，`支付金额与订单应付金额不一致`；
5. 同订单支付记录已存在 → `500`，`支付数据不一致`。

支付成功时以下变化必须同时生效：

```text
创建支付记录：
    订单编号 = 当前订单编号
    支付金额 = 本次支付金额
    支付时间 = 操作时间

订单状态 = 已支付
```

支付不会改变库存。

成功返回 `200`：

```json
{
  "订单编号": 101,
  "订单状态": "已支付",
  "支付金额": "200.00",
  "支付时间": "2026-01-08T00:00:00.000Z"
}
```

### 6.2 取消订单

请求：

```http
POST /orders/{id}/cancel
```

错误检查顺序：

1. 订单不存在 → `404`，`订单不存在`；
2. 状态既不是 `未支付` 也不是 `已取消` → `409`，`订单状态不允许取消`；
3. 对应商品库存不存在 → `500`，`库存数据不一致`。

当状态为 `未支付` 时，以下变化必须同时生效：

```text
订单状态 = 已取消
库存数量 = 库存数量 + 购买数量
```

当状态已经是 `已取消` 时：

- 返回成功；
- 订单和库存都不改变；
- 不得再次回补库存。

成功返回 `200`：

```json
{
  "订单编号": 101,
  "订单状态": "已取消",
  "库存数量": 12
}
```

### 6.3 退款

请求：

```http
POST /orders/{id}/refund
Content-Type: application/json
```

```json
{
  "userId": 1,
  "amount": "100.00",
  "quantity": 1
}
```

第一里程碑把 `userId` 视为可信测试输入，用于查询角色；鉴权和防冒用不属于当前范围。

退款错误检查顺序固定为：

1. 订单不存在 → `404`，`订单不存在`；
2. 订单状态不是 `已支付` → `409`，`订单状态不允许退款`；
3. 支付记录不存在 → `500`，`支付数据不一致`；
4. 商品库存不存在 → `500`，`库存数据不一致`；
5. 用户不存在 → `404`，`用户不存在`；
6. 普通用户超过支付后 7 天 → `403`，`已超过普通用户退款期限`；
7. 退款数量小于或等于 0 → `400`，`退款数量必须大于零`；
8. 退款金额小于或等于 0 → `400`，`退款金额必须大于零`；
9. 退款金额不等于 `商品单价 × 退款数量` → `400`，`退款金额与退款数量不一致`；
10. 退款数量超过 `购买数量 - 已退款数量` → `409`，`退款数量超过可退款数量`；
11. 退款金额超过 `支付金额 - 已退款金额` → `409`，`退款金额超过可退款金额`。

管理员跳过第 6 项时间检查，但不跳过其他任何规则。

退款成功时以下变化必须同时生效：

```text
订单的已退款金额 += 本次退款金额
订单的已退款数量 += 本次退款数量
库存数量 += 本次退款数量
```

如果新的已退款金额等于支付金额，并且新的已退款数量等于购买数量：

```text
订单状态 = 已全部退款
```

否则订单状态保持 `已支付`。

成功返回 `200`：

```json
{
  "订单编号": 101,
  "订单状态": "已支付",
  "本次退款金额": "100.00",
  "累计退款金额": "100.00",
  "本次回补数量": 1,
  "库存数量": 11
}
```

### 6.4 查询可退款金额

请求：

```http
GET /orders/{id}/refundable
```

错误检查顺序：

1. 订单不存在 → `404`，`订单不存在`；
2. 订单状态不是 `已支付` → `409`，`订单当前不可退款`；
3. 支付记录不存在 → `500`，`支付数据不一致`。

计算：

```text
可退款金额 = 支付金额 - 已退款金额
可退款数量 = 购买数量 - 已退款数量
```

成功返回 `200`：

```json
{
  "订单编号": 101,
  "可退款金额": "100.00",
  "可退款数量": 1
}
```

## 7. 失败原子性

支付、首次取消和退款都是原子业务操作。

只要流程返回失败，下列任何可观察状态都不能发生改变：

- 订单状态；
- 已退款金额；
- 已退款数量；
- 支付记录；
- 库存数量。

原子性不能通过“当前实现碰巧把检查写在改变之前”推断，必须在 AAL 中可见，并由语言标准给出统一提交保证。

## 8. 传输错误与业务错误

非法 JSON、字段缺失、字段类型错误和非法金额编码属于传输输入错误，在进入流程前返回 `400`。

响应固定为：

```text
非法 JSON          → 请求 JSON 无效
缺少必填字段        → 缺少字段：<外部字段名>
字段基础类型错误     → 字段类型错误：<外部字段名>
人民币金额编码错误   → 金额格式错误：<外部字段名>
```

同一请求存在多个字段问题时，按 HTTP 入口中映射字段的声明顺序检查，返回第一个错误。未映射的额外 JSON 字段被忽略，不能进入流程或影响结果。

只有请求成功通过传输解析后，才适用各流程列出的业务错误优先级。

所有已声明的业务失败和传输输入失败使用：

```json
{
  "error": "明确的中文失败消息"
}
```

未匹配路由返回 `404` 和 `{"error":"Not found"}`；未处理 Runtime 错误返回 `500` 和 `{"error":"Internal server error"}`。

## 9. Fixture 与测试隔离

订单、库存和用户由冻结 fixture 提供。Fixture 是可见测试数据，不包含业务行为。

每个 Oracle 场景必须从声明的 fixture 快照和固定操作时间开始，不能依赖前一个独立场景留下的状态。一个场景内部可以连续发送多个请求，以验证状态变化、重复操作和失败后不改变。

Fixture 摘要和固定时钟必须写入 Oracle 测试结果，但不计入 AAL 审计面积。

## 10. 第二里程碑：requestId 幂等

第二里程碑再增加：

```text
退款请求编号：文本
退款记录
可选查询
第一次结果重放
同一 requestId 跨订单复用冲突
重复请求不再次退款、不再次回补库存
```

在语言支持可选查询和条件成功之前，不允许由 Runtime 私自实现幂等。
